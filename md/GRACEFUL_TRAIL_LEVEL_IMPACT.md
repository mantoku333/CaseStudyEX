# 優雅Trail レベル表現 / ゲージ吸収 / 滑空継続 / Lv1無得点

前回の修正（`GRACEFUL_TRAIL_LEVEL_FAILURE_ANALYSIS.md`）で色破損は直りましたが、
Lv3・Lv4が「Lv2とほとんど同じに見える」状態が残っていました。
一度は粒の量で解決しようとしましたが、それは「ごちゃついて気持ち悪い」だけでした。
現在は参考イメージの方針どおり、**Lv1をベースに、上がるのはトレイル側**という作りです。

## 1. レベルはトレイルで見せる。粒は増やさない

参考イメージ（アルカンシェル 優雅アクション エフェクト3段階比較）の方針に合わせ、
**Lv1をベースに、上がるのはトレイル（霧のリボン）の側**という作りにしました。
粒を増やして密度で押すのは「ごちゃつき」にしかならないため、
スプライト系の発生量・サイズ・散布半径は**Lv2で頭打ち**にしています。

| | Lv1 | Lv2 | Lv3 | Lv4 |
| --- | ---: | ---: | ---: | ---: |
| 細粒 発生率/距離 | 5.000 | 6.917 | 7.608 | 8.300 |
| 花びら 発生率/距離 | 0.420 | 0.539 | 0.539 | 0.539 |
| 花びら サイズ | 0.7200 | 0.7200 | 0.7200 | 0.7200 |
| 散布半径 | 0.894 | 1.043 | 1.043 | 1.043 |
| **リボンの線（同時本数）** | **2** | **2** | **4** | **5** |
| **リボンの色味（白からの差）** | **0.000** | **0.043** | **0.125** | **0.239** |
| 光彩（SoftGlow）サイズ | 2.2345 | 2.5325 | 3.1842 | 3.9104 |

計測値: `Temp/GracefulTrailVerification/LevelImpact.txt`。

### 上がるもの

- **リボンの本数。** 3本から5本に増設し、`Ribbon_Flourish`（Lv2.6から）と
  `Ribbon_Halo`（Lv3.1から）を追加。各リボンが自分の出現レベル・バースト開始遅延・
  バースト長を持ち、1レベルかけて滲み出るように現れます。
- **リボンの色。** `GracefulPalette.RibbonTint` を新設し、白を土台に色を少しずつ足します。
  **Lv1は純白のまま**（差0.000）、Lv2でごくわずかな青紫、Lv3でピンクと水色、
  Lv4で淡い虹の彩りが軌跡に沿って流れます。色は白に**加える**だけで、白を置き換えません。
  Lv2の色味は0.043＝ほぼ知覚できない量に抑えてあります。
- **リボンの幅・長さ。** Lv2までの従来カーブのまま（Lv4で幅2.15倍、長さ1.5倍）。
  Lv3以上の上乗せは「髪の毛」に見えたため撤去しました。濃さのみLv4で1.2倍。
- **リボンの出方。** Lv1・Lv2は従来どおり短い霧が途切れながら流れます。Lv3以上は
  ラインがサイクル上に配られ、重なりで継ぎ目が見えなくなります。下の「途切れの修正」を参照。
- **光彩（SoftGlow）だけはふくらむ。** 輪郭を持たないので混雑にならず、
  「溢れる光彩」を担当します。Lv4でサイズ1.75倍。

### 上がらないもの

- **花びら。** サイズも数もLv2で止まります（サイズは全レベルLv1と同一）。
  参考イメージの「花びらは主役にせず、少量を遅れて流す」に合わせています。
- **細粒・光粒・星のサイズ**、および**散布半径**。Lv2の値で頭打ちです。
- **細粒の数**は、リボンのバースト周期に合わせてLv4で+20%だけ。実数でもLv2の38粒に対しLv4は約48粒です。
- 閃きバーストは細粒4・星1まで。成功時の放出量もLv4で1.4倍に留めています。
- 各レイヤーの`maxParticles`は96から320へ上げてありますが、
  これは発生率が静かに切り捨てられないための余裕で、実際の同時表示数はLv4でも細粒50粒程度です。

### 途切れの修正（Lv3・Lv4）

滑空中にLv3・Lv4のトレイルが途切れる問題がありました。計測すると、原因は
「リボンが消える時間が長い」ことではなく、**線が増えたこと自体**でした。

各リボンは自分のバースト窓を持ち、窓の外では履歴を捨ててゼロ長からやり直します。
線が1〜2本のLv1・Lv2ではこれが「霧が途切れながら流れる」表現になりますが、
4〜5本になると、**全ラインが同じサイクル境界で一斉に出入りする**ため、
短い断片が同時に生まれ直し、ちぎれた軌跡に見えていました。

一度は「Lv3以上は常時オン」にしましたが、それは長い帯が何本も貼り付いたまま残り、
**髪の毛がくっついているように**見えるだけでした。正解は常時オンではなく、
**ラインをサイクル上に配り、重なりで継ぎ目を隠す**ことです。

`IsBurstActive` に `spread = InverseLerp(2, 3, visualLevel)` を渡し、
各ラインの開始位置を `Lerp(元の遅延, サイクル長 × 自分の位相, spread)` で決めます。
位相はMain 0、Accent 0.18、Veil 0.36、Flourish 0.55、Halo 0.73。
Lv2以下ではspreadが0なので**計算式も結果も従来と完全に同一**です。

あわせて、リボンの幅と長さのLv3以上の上乗せ（従来1.5倍・1.4倍）を撤去しました。
太く長い帯が何本も出ることが「髪の毛」の直接の原因だったためです。

滑空中の計測（240フレーム、等速の斜め降下）:

| | Lv1 | Lv2 | Lv3 | Lv4 |
| --- | ---: | ---: | ---: | ---: |
| リボン表示率（継ぎ目の無さ） | 46.7% | 52.8% | **100.0%** | **100.0%** |
| 完全な空白フレーム | 21/180 | 6/180 | **0** | **0** |
| 最も長く出ているラインの占有率 | 47% | 53% | **64%** | **74%** |
| 同時に出ているライン数（平均） | 0.69 | 0.89 | **1.91** | **2.55** |

Lv3・Lv4は継ぎ目ゼロでありながら、どのラインも常時オンではなく（最大74%）、
同時に出ているのは平均2本前後です。1本の帯が貼り付いたままにはなりません。

### リボンが増えるタイミング（Lv3から）

`Ribbon_Veil` は従来Lv2.05から滲み出ていたため、Lv2→Lv3の上昇中に3本目が見えていました。
出現レベルとフェード幅を分離し（`fadeInSpan`）、**追加ラインがLv3の直前まで出ない**ようにしました。

| ライン | 出現レベル | フェード幅 | 全開 |
| --- | ---: | ---: | ---: |
| Ribbon_Main / Accent | — | — | 常時（Lv1から） |
| Ribbon_Veil | 2.80 | 0.20 | Lv3.0 |
| Ribbon_Flourish | 2.85 | 0.15 | Lv3.0 |
| Ribbon_Halo | 3.50 | 0.50 | Lv4.0 |

結果、本数はLv1=2、Lv2=2、Lv3=4、Lv4=5。Lv2.80まで追加ラインが1本も出ないことを
検証でアサーションしています。

### Lv1は一切変更していない

`flourish = InverseLerp(2, 4, visualLevel)` と `sprite = Min(t, 1/3)` はいずれも
Lv1で倍率1.0になります。検証では、Lv1の適用値がプレハブの記述値と**完全に一致**すること
（発生率5.000、半径0.894、花びらサイズ0.7200、光彩サイズ2.2345、リボン色味0.000）を
アサーションで固定しました。

## 2. ゲージ吸収を同じエフェクトで作り直した

従来は、加点時に別のパーティクル（白青の丸い粒）を新規生成してゲージへ飛ばしていました。
プレイヤーが直前まで見ていた軌跡とは無関係の見た目です。

現在は、**その軌跡そのものがゲージへ吸い込まれます**。

1. `PlayerGracefulActionEffectManager.TryAttractLiveParticles` が `PlayerMovementTrail` に委譲。
2. `PlayerMovementTrail.TryAbsorbIntoGauge` が、確定したレベルの設定のまま
   別れ際のひと掴み（細粒8・光粒3・星2・花びら1）を放ち、新規発生を止めます。
3. 生きている粒すべてに `ElegantPointLiveParticleAttractor` を付け、
   ベジェの弧＋渦を描いてHUDゲージへ運びます。
4. リボンの帯は引っ張らず、従来どおり自然にフェードさせます。帯を曲げると形が壊れるためです。

### 吸い寄せ方（急に固まらないこと）

「綺麗に舞っていたエフェクトが急に固まって挙動を変える」のを避けるため、引き継ぎを段階的にしました。

- **自由位置を並走させる。** 各粒が本来の漂い・上昇・ノイズで動いた分を毎フレーム加算し続け、
  その自由位置と飛行経路を `Smooth01(進行度)` で混ぜます。開始直後は自由位置がほぼ100%なので、
  粒は漂ったまま徐々に引かれていきます。検証上、引き継ぎ1フレーム目の移動量は0.0031ワールド単位で、
  瞬間的な飛びはありません。
- **寿命を伸ばさず、飛行時間へ引き伸ばす。** 従来は`remainingLifetime`を単純に伸ばしていたため、
  消えかけの粒が寿命カーブの先頭へ戻り、**急に明るくなって**いました。
  現在は正規化した経過位置を保ったまま`startLifetime`を引き伸ばすので、
  色も大きさも連続したまま、ちょうどゲージに着く頃に自分のフェードを完了します。
- **アルファと大きさを落としながら運ぶ。** 引かれる強さに応じてアルファを35%、大きさを45%まで
  落とします。検証では平均アルファが195.1→61.2へ下がっています。
- **出発をばらけさせた。** 開始遅延の幅を0.28秒から0.45秒へ。一斉に飛ばず、順に掬われていきます。
- **到達時の即死をやめた。** 距離で`remainingLifetime = 0`にしていたのを廃止し、
  上の寿命引き伸ばしによる自然消滅に任せています。

あわせて2点直しました。

- **吸引対象を確定時のスナップショットに限定。** 従来は毎フレーム現存する全粒を掴んでいたため、
  飛行中に次の連続が始まると、生まれたての軌跡までゲージへ引きずられていました。
- **ゲージの脈動を到着に合わせた。** 従来は加点の瞬間（=光が飛び立つ瞬間）に1.08倍・0.16秒で
  跳ねており、光が着く1.4秒前に反応していました。現在は移動時間の82%後に1.16倍・0.34秒で膨らみます。

予備経路（軌跡が存在しない場合の生成バースト）も、`GracefulPalette` を新設して
軌跡と同じパステルスペクトラムを共有させています。

## 3. 滑空中に精算されない

滑空の途中で優雅ゲージに回収されてしまう問題がありました。原因は
`PlayerElegantPointController.IsSuccessfulActionHeld` が **連続の最後の成功**だけを見て
継続判定していたことです。滑空中に回避や反動が成功すると`LastAction`がそちらに移り、
滑空自体は続いているのに継続条件が滑空を見なくなって、1秒後に時間切れ精算していました。

現在は、**現在進行中の持続アクションがあれば**、それが最後の成功かどうかに関係なく窓を保ちます。

- 滑空中（`IsGlideMotionActive`）→ 保持。途中で回避や反動が成功しても切れません。
- 実際に滑空が終わる（着地・傘を閉じる・上昇に転じる）→ そこから1秒で精算。
- 滑空が中断した場合に時間切れ→再開でLv1から始まる従来の挙動は変わりません
  （`InterruptedGlideSession_ExpiresAndResumesAtLevelOne` で確認）。

## 4. ゲージの増え方と、吸収とのタイミング

残高の計算（`ElegantPointWallet.Add`）は単調増加なので、おかしかったのは演出側です。

### 一度減って増えて見えた

`ElegantPointGainVfxController` の脈動が `AbsorbTargetRect` を対象にしていましたが、
これは**ゲージのFill（バーそのもの）**でした。Fillはピボット(0,1)・幅が残高そのものなので、
`localScale` を1.16倍にすると**バーが伸びて縮む**＝残高が動いたようにしか見えません。
さらに `Refresh` が残高変化のたびに `localScale = Vector3.one` を書き込むため、
脈動中に次の加点が入るとスケールが1へスナップし、縮んでから再び伸びていました。

### ゲージ全体のスケールが微妙に変わる

脈動の対象をゲージの枠に移し縦方向のみにしましたが、それでもゲージ全体が伸縮していました。
**スケールによる演出そのものを廃止**しています。
`ApplyView` は毎回 Fill と枠の `localScale` を `Vector3.one` に書き戻すので、
どこかに残ったスケールも消えます。代わりの反応は、
バーが伸びる動きそのものと、Fillの色が一瞬白く寄る発光（0.3秒）です。幾何は一切動きません。

### 吸収されてからゲージが増える

従来は加点と同時にバーが即座に伸び、その1.2〜1.45秒後に光が到着していました。順序が逆です。

`ElegantPointHudView` が表示用の残高 `displayedBalance` を持つようにしました。

1. `ElegantPointWallet` は従来どおり即座に加算されます（セーブや消費に影響しません）。
2. `Refresh` は目標値を受け取るだけで、バーは動かしません。
3. `ElegantPointGainVfxController` が吸収を開始したとき、
   `HoldGainUntilAbsorbed(移動時間 × 0.82)` でバーを保留させます。
4. 保留が明けると、`gainFillSeconds`（0.38秒）かけて目標値まで伸び、数字も一緒に上がります。

減少（消費・ロード・リセット）は待たせず即座に反映します。プレイヤーが飛んでくるのを
見守る種類の変化ではないためです。

## 5. 足元から出ていたのを腰の位置へ

軌跡が足首のあたりから出ていました。腰のオフセットが**二重に適用**されていたためです。

1. `GracefulTrailBuilder.Install` が、シーンの`FX_Trail`をすでに腰の高さ
   （スプライト中心から身長の12%下）に置いています。
2. その上で、プレハブ内の各レイヤーとリボンが `-height * 0.16` だけさらに下げられていました。
3. しかもこのオフセットはプレハブローカル単位なので、プレイヤーのスケール1.59倍が掛かります。

実測では、身長5.58に対して発生位置が足元から0.70（**身長の12.5%**）の高さでした。

プレハブ内の追加オフセットを撤去し、リボン同士のわずかな上下差（±0.1〜0.24）だけを残しました。
現在の発生位置は**身長の43.0%**、つまり腰の高さです。

再発防止として、実際に生まれた粒の平均高さがスプライト境界の28%〜72%に収まることを
`VerifyEmissionHeight` で検証しています。修正前の12.5%はこの検査で落ちます。
計測値: `Temp/GracefulTrailVerification/EmissionHeight.txt`。

## 6. Lv1ではポイントを増やさない

`ElegantActionChain.MinimumRewardedActionCount = 2` を追加し、
**連続数が1で終わった場合の報酬を0**にしました。`Advance`（時間切れ精算）、`Settle`（死亡・破棄）、
`CalculateReward` のすべてが同じ判定を通ります。

- 滑空1回だけで終了 → 0ポイント。加点イベントが発生しないので、ゲージ吸収演出も起きません。
- Lv2以上で終了 → 従来どおり連続数×10ポイント（Lv2なら20）。
  「1回目を差し引く」方式ではなく、連続全体を支払います。

内部レベル自体はLv1から立ち上がり、軌跡もLv1から出ます。変えたのは支払いだけです。

## 7. 検証

`Tools > Effects > Verify Graceful Movement Trail`（プレハブ再生成＋描画検証）

- パーティクル構成が5スプライト層＋5本のリボン＋10本のフェード帯であること。
- 粒の発生位置が身長の28%〜72%（腰の高さ）にあること。実測は52.6%。
- **Lv1の適用値がプレハブの記述値と完全一致**すること（倍率が一切掛からないこと）。
- 細粒がLv2の1.35倍を超えないこと、花びらの発生率がLv2の1.05倍を超えないこと。
  実測は1.20倍と1.00倍。
- **花びらのサイズが全レベルで同一**、**散布半径がLv2とLv4で同一**であること。
- リボンの同時本数がLv2 < Lv3 < Lv4。実測は2 < 4 < 5。
- リボンの色味がLv1で0、以降レベルごとに増えること。実測は0.000 / 0.043 / 0.125 / 0.239。

`Tools > Effects > Verify Ribbon Continuity`（滑空中のトレイル連続性）

- Lv1・Lv2のリボン表示率が70%未満であること（従来の途切れる表現が保たれていること）。
- Lv3・Lv4のリボン表示率が100%、完全な空白フレームが0であること（継ぎ目が出ないこと）。
- Lv3・Lv4で最も長く出ているラインの占有率が90%以下であること（貼り付いた帯が無いこと）。
- 同時に出ているライン数の平均が3.2本以下であること（帯のカーテンになっていないこと）。
- 追加ライン（Veil / Flourish / Halo）がLv2.80まで一度も出ないこと。
- 落ち着いたストロークの頂点間隔÷太さが0.5未満であること。
- 連続遷移検証から自動で呼ばれます。計測値: `Temp/GracefulTrailRegression/RibbonContinuity.txt`。
- 既存の検証（移動・停止・寿命保持・テレポート・ポーズ・144fps・レベル上限）は従来どおり通過。

`Tools > Effects > Verify Trail Continuous Transitions`（連続遷移＋吸収）

- 30/60/144fpsで Lv1→2→3→4→0 を3周し、全補間フレームでRGBが0.75以上。
  最小値はLv1=0.930000、Lv2=0.892667、Lv3=0.855333、Lv4=0.818000で、周回しても同じ値に戻ります。
- 停止中の成功通知8種類が、ヒットストップ後に1回だけ表示される。
- 吸収検証: Lv3で軌跡を作った後、111粒を捕捉。
  引き継ぎ1フレーム目の移動量0.0031（飛びがない）、ゲージまでの平均距離 9.502 → 最接近0.018、
  平均アルファ 195.1 → 61.2（運びながら薄くなる）、飛行終了時に残存0。

NUnit: 54件中53件成功。残る1件 `HudFillRect_RepresentsHalfBalanceWithoutRequiringASprite` は
既存HUDのレイアウト期待値不一致で、前回から変わらず今回の変更とは無関係です。
Lv1無得点・Lv2以上支払いの規則は `ElegantActionChainTests` に追加した
`LevelOnePaysNothing_AndLevelTwoPaysTheWholeChain`、
滑空継続中に精算されないことは `SuccessDuringGlide_DoesNotSettleWhileTheGlideContinues`、
ゲージが吸収を待ってから伸びること・Fillと枠が一度もスケールされないことは
`Gauge_WaitsForTheAbsorptionThenFillsWithoutEverScaling` で確認しています。

これらはEditor上での実プレハブ・実ParticleSystemによる自動検証です。
入力操作による全ゲームプレイの網羅検証とは区別します。
