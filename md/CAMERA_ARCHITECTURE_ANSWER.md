# 2Dアクションのカメラ、何が正解か — 全面調査と結論

結論を先に: **エリアごとにカメラを置く方式をやめる。カメラは1台にして、常にプレイヤーを追い、
いまいる領域の矩形で軸ごとにクランプする。** それだけで今の問題のほとんどが構造的に消えます。

「場所によって毎回調整しないといけないのは変」という直感は正しいです。
調整が必要なのは設計のせいで、作り込みが足りないからではありません。

---

## 1. なぜ毎回おかしくなるのか

このプロジェクトのカメラは、実は**3つの別々の機構**を部屋ごとに手で割り当てています。

| 機構 | 部屋数 | 中身 |
|---|---|---|
| 固定エリアカメラ | 31 | 部屋ごとに `CinemachineCamera` を手で配置 |
| フリー追従カメラ | 23 | `CN_FollowCam` を共有。**範囲制限なし** |
| 自前の横追従 | 7 | `transform.position` を手で SmoothDamp |
| ＋ その間をつなぐポータル | 63 | さらに4つ目のカメラを生成して補間 |

**4種類の挙動が混在し、その境目ごとに手当てが要る。** だから場所ごとの調整が無限に出てきます。
私がこれまで直してきたものは、ほぼ全部「どれか2つの機構の境目」で起きていました。

### 決定的な数字：44%の部屋は視野に収まらない

ortho 12 の視野は 42.7 x 24.0。全57部屋を分類すると:

| 分類 | 部屋数 | 例 |
|---|---|---|
| 両方収まる（静止でよい） | **32** | 38.3 x 20.3 の標準部屋 |
| 縦追従が必要 | **12** | Col_210 = 38.9 x **80.0**、Col_319 = 7.8 x **71.6** |
| 横追従が必要 | **7** | Col_105 = **163.1** x 20.3 |
| 縦横とも追従が必要 | **6** | Col_223 = **76.3 x 90.0** |

**25部屋（44%）が視野に収まりません。** 高さ80uの部屋を高さ24uの視野で見せています。

この25部屋に対する仕組みが、横7部屋ぶんの自前実装しかありません。
残り18部屋は「フリー追従カメラ（範囲制限なし）」に丸投げされていて、
だから部屋の外が見えるし、挙動が他と揃いません。

## 2. 「ステージ最初の上に上がるところ」が最低な理由

実測しました。下から上へ、4部屋です。

| 部屋 | 高さ範囲 | サイズ | 機構 | 視野 |
|---|---|---|---|---|
| Col_107 | -62.6 .. -42.4 | 133.9 x 20.3 | **自前の横追従** | — |
| Col_112 | -42.9 .. -22.3 | 9.0 x **20.6** | **固定カメラ** | 32 x **18** |
| Col_106 | -22.5 .. -2.2 | 14.1 x 20.3 | **固定カメラ** | 36 x 20 |
| Col_104 | -2.5 .. 15.1 | 20.4 x 17.5 | **フリー追従** | — |

問題が3つ重なっています。

1. **4部屋で3つの機構を渡り歩く。** 横追従 → 固定 → 固定 → フリー追従。
   境目が3回あり、そのすべてが機構の切り替わり。
2. **登る縦穴 Col_112 は高さ20.6u、視野は18u。**
   部屋のほうが2.6u高いので、**登っている最中にプレイヤーが画面外に出ます。**
   全57部屋中、プレイヤーが画面外に出られるのはここと Col_109 の2部屋だけ。
   その1つが「最初の上昇」に置かれている。
3. **Col_112 は幅9uなのにカメラは32u映す。** 縦穴の3.5倍の幅、
   つまり画面の7割が隣の部屋か暗闇です。

「本当に最低」は正確な評価でした。**設計上、ここは良くなりようがありません。**

## 3. 2Dアクションのカメラの定石

調べた結果、業界の標準解ははっきりしています。

### 基本形

> カメラをプレイヤーに追従させ、**部屋の境界で、半画面ぶん内側に寄せてクランプする**

ある解説はこう書いています。カメラ位置を決めた後に境界へクランプし、
その境界はカメラが通常プレイヤー中心にあることを見込んで半画面ぶん詰める、と。

### 「Celeste方式」

GameMaker向けのカメラ資産の更新履歴に、まさにこの条件分岐が出てきます。

> bound オブジェクトが view より大きいときだけプレイヤーを追従する

**これは私が部屋データから導いた「軸ごとに max(部屋, 視野)」と同じルールです。**
別経路で同じ結論に到達しているので、ルール自体は妥当と考えてよいはずです。

### 既知の落とし穴

同じ資料が警告しています。

> 追従中に境界を差し替えると、カメラが即座に新しい境界へクランプされてガクつく

**これは今まさに起きていることです。** 部屋をまたぐ瞬間に制限が変わるので、
対処しないと必ず跳ねます。後述の設計はここを明示的に扱います。

### 理論的背景

Itay Keren の GDC 2015「Scroll Back: The Theory and Practice of Cameras in Side-Scrollers」が
この分野の定番資料です。側スクロールのカメラ技法を1980年代から現代まで体系化していて、
「何を見せるべきか」「それをどう滑らかに快適に見せるか」を軸に整理しています。
先読み（プレイヤーの数ミリ秒先を狙う）なども扱っています。

## 4. 提案する設計

### たった1つのルール

```
カメラは常に1台。常にプレイヤーを追う。
いまいる領域の矩形に対して、軸ごとに:

    領域サイズ <= 視野サイズ  →  その軸は領域の中心に固定
    領域サイズ >  視野サイズ  →  その軸は追従し、領域の端でクランプ
```

このルールが、今3つの機構に分かれているものを**全部1つに畳みます**。

| 部屋 | ルールの結果 | 今の機構 |
|---|---|---|
| 38.3 x 20.3 標準部屋 | XY固定 = **今の固定カメラと同じ絵** | 固定カメラ |
| Col_105 163 x 20.3 | X追従 / Y固定 = **横スクロール** | 自前の横追従 |
| Col_112 9.0 x 20.6 | X固定 / Y追従 = **縦スクロール** | 固定（破綻中） |
| Col_223 76 x 90 | XY追従 = **自由追従＋範囲制限** | フリー（無制限） |

**部屋ごとのモード指定は不要です。** 矩形と視野を比べるだけで決まります。
57部屋すべてが、コライダーの矩形から自動で正しくなります。

### これで何が構造的に消えるか

| 今の問題 | なぜ消えるか |
|---|---|
| 切り替えが急 | **切り替えが存在しない**。カメラは1台で、連続的に動く |
| プレイヤーを見失う | 画面内の位置が常に一貫する。飛ばない |
| プレイヤーが見切れる | クランプが視野を領域内に保つので**原理的に不可能** |
| 部屋の外が見える | 同上。31/32本の問題が消える |
| Fogのチカチカ | カメラが切り替わらないので同期ズレが起きない |
| 往復でガクガク | 境界をまたいでもカメラが切り替わらない |
| 場所ごとの調整 | ルールが1つなので調整箇所がない |

### 唯一の本質的な作業：領域の矩形を引く

これは**今すでにある**（`Col_*` の BoxCollider2D、57個）。流用できます。

## 5. なぜ Confiner2D ではなく直接クランプか

前回 `CinemachineConfiner2D` を勧めましたが、**このプロジェクトには過剰です。**

| 観点 | Confiner2D | 直接クランプ |
|---|---|---|
| 対応形状 | 任意の多角形 | 軸平行の矩形のみ |
| このプロジェクトの形状 | **全72個が BoxCollider2D = 矩形** | ちょうど合う |
| 計算 | 多角形を内側にオフセットする前計算（ベイク） | `Mathf.Clamp` 2回 |
| 領域切り替え | 形状を差し替えるとキャッシュが無効化、再ベイク | **コストゼロ** |
| Unityの公式見解 | 「差し替えを繰り返すより、カメラを複数持ってブレンドしろ」 | 制約なし |

矩形しかないのに多角形のベイク機構を使う理由がありません。
直接クランプなら約10行で、領域の差し替えが自由にできます。

```csharp
// 軸ごとに: 領域が視野より小さければ中心、大きければ端でクランプ
float halfW = ortho * aspect, halfH = ortho;
pos.x = region.width  <= halfW*2 ? region.center.x
      : Mathf.Clamp(pos.x, region.xMin + halfW, region.xMax - halfW);
pos.y = region.height <= halfH*2 ? region.center.y
      : Mathf.Clamp(pos.y, region.yMin + halfH, region.yMax - halfH);
```

領域が切り替わる瞬間のガクつき（前述の既知の落とし穴）は、
**クランプ矩形そのものを0.2〜0.3秒で補間する**ことで吸収します。
カメラ位置を補間するのではなく制約を補間するので、プレイヤー追従は一切途切れません。

## 7. 残る、本当に必要な調整

ルールで決まらないのは次の3つだけです。これは設計判断なので手で決める価値があります。

| 項目 | 内容 |
|---|---|
| デッドゾーン | プレイヤーが少し動いてもカメラが動かない範囲。歩くたびに揺れるのを防ぐ |
| 先読み（look-ahead） | 進行方向を少し先に見る。既存の `FollowCameraFacingBias` の発想は正しい |
| 領域の切り方 | どこを1つの領域にするか。広く取れば切り替えが減り、狭く取れば構図を作り込める |

3番目が重要です。**いまの「部屋」は小さすぎます。**
水平に連続した部屋をまとめて1領域にすれば、その区間の切り替えは完全に消えます。
実測では13の連なりが見つかっていて、19箇所の切り替えが消せます。

## 8. 移行の手順

既存を壊さずに進められます。

1. `GameplayCamera`（1台）+ 領域クランプ拡張を新規に作る
2. `RoomCameraTrigger` に「領域矩形を返す」役だけ残す（既にある）
3. 新シーンで、固定カメラ31本とポータル63個を無効化し、新カメラ1台に任せる
4. 走ってみて、デッドゾーンと先読みだけ詰める
5. 領域をまとめたい区間だけ、矩形を広げる
6. 問題なければ旧コード3,655行を削除

ステージ最初の上昇（Col_107→112→106→104）が一番わかりやすい検証区間です。
いま3つの機構を渡り歩いて破綻している場所が、1つのルールで通るはずです。

## 9. 訂正と補足：「エリア全体を見せる」方針は変えなくてよい

### この方針とルールは同じもの

```
今の方針                          提案したルール
エリアはエリア全体を見せる      =  領域 <= 視野 → 中心に固定
広いエリアはそこに合わせた追従  =  領域 >  視野 → 追従＋端でクランプ
```

**ルールは方針を式にしただけです。** 変わるのは「どう実現するか」だけで、見せ方の方針は維持されます。
部屋ごとに3つの機構へ手で割り当てるのをやめ、矩形と視野の比較から自動で決める、という違いです。

### 訂正：切り替えは全部は消えない

§4 で「切り替えが存在しない」と書いたのは**言い過ぎでした。** 実測します。
隣接する部屋ペア75組の内訳:

| 境目の種類 | 組数 | 1台方式にしたときの挙動 |
|---|---|---|
| 収まる ↔ **広い** | 39 | **解決する**。広い側のカメラは既にプレイヤー近傍にいるので移動量が小さい |
| **広い** ↔ **広い** | 17 | **解決する**。同上 |
| 収まる ↔ 収まる | **19** | **残る**。両側とも中心固定なので、カメラは約38u動く必要がある |

**75組中56組（75%）は解決します。** 残る19組は、
「両方のエリアがエリア全体を見せる」という方針そのものから来る移動なので、
実装を変えても消えません。方針を保つ以上、ここは残ります。

残る19組（抜粋）: Col_103↔104 / Col_106↔101 / Col_112↔106 / Col_201↔202 /
Col_211↔212 / Col_215↔216 / Col_217↔216 / Col_218↔219 / Col_304↔305 / Col_306↔307 ...

### 訂正：「部屋の外が見える」も全部は消えない

クランプが保証するのは「**プレイヤーが画面外に出ないこと**」です。
領域が視野より小さい軸では、視野のほうが大きいので**必然的に領域の外が映ります**。
32部屋（収まる側）では今と同じく外が見えます。これは方針の帰結であって不具合ではありません。

構造的に消えるのは次の2つです。

- **プレイヤーの見切れ**（領域 > 視野 の軸でクランプが効くため）
- **3機構の境目で起きる不具合**（機構が1つになるため）

### Col_112 はルールだけで直る

最初の上昇が破綻している直接の原因は、**CN_112 の ortho が 9 だから**です。

```
Col_112      9.0 x 20.6
CN_112 ortho 9  → 視野 32.0 x 18.0   ← 18 < 20.6 なので縦に 2.6u はみ出す
統一 ortho 12   → 視野 42.7 x 24.0   ← 20.6 <= 24 なので縦穴全体が収まる
```

**ortho を 12 に揃えるだけで、縦穴全体が画面に入り、見切れが消えます。**
同じく Col_109（38.8 x 28.7）は 28.7 > 24 なので縦追従に切り替わり、やはり見切れません。

### 残る19組をどうするか：領域の粒度

ここが唯一の設計判断です。**「エリア」の単位をカメラ側で少し大きく取れます。**

部屋（`Col_*`）は Fog・敵・ミニマップが使うのでそのまま残し、
**カメラ用の領域矩形だけを別に、連続した区間はまとめて1つ**にします。

最初の上昇で言えば:

```
現状: Col_112 (9.0 x 20.6) → Col_106 (14.1 x 20.3)   縦に20uの移動が発生
統合: 112+106 を1領域 (14.1 x 40.7) → 縦追従になり、登る間ずっと繋がる
```

これは「エリア全体を見せる」方針と矛盾しません。**エリアの大きさを適正にするだけ**です。
水平方向では13の連なりが見つかっていて19箇所、垂直方向にも同様の統合先があります。

まとめる区間は全部でなくてよく、**往復や上下移動が多い場所だけ**で効果があります。

## 10. ortho を調べて分かったこと：**設計は正しかった。足りないのはクランプ1つだけ**

### 部屋ごとの ortho 上書きが見つかった

`_overrideDefaultFollowCameraOrthographicSize` が有効な部屋が5つありました。
（私は以前「0部屋」と報告しましたが、一部しか確認していませんでした。誤りです）

| 部屋 | 部屋サイズ | 上書き ortho | 収めるのに必要 | 結果 |
|---|---|---|---|---|
| Col_210 | 38.9 x **80.0** | 16.0 | 40.0 | 追従が必要 |
| Col_214 | 38.0 x **60.8** | 16.0 | 30.4 | 追従が必要 |
| Col_310 | 58.1 x 51.7 | 16.0 | 25.9 | 追従が必要 |
| Col_317 | 58.7 x 50.4 | 16.0 | 25.2 | 追従が必要 |
| Col_313 | 38.3 x 40.5 | 16.0 | 20.3 | 追従が必要 |

**5部屋とも ortho 16 に揃えてあります。** つまり:

> 広い部屋では、フリーカメラを 12 → 16 にズームアウトしたうえでプレイヤーを追従させる

これは「広いエリアはそこに合わせたプレイヤー追従カメラ」という方針**そのもの**です。
手で一貫して設定されています。

### 結論：方針は正しく、実装に1つだけ欠けている

整理するとこうなっています。

| モード | 対象 | 状態 |
|---|---|---|
| 静止（エリア全体を見せる） | 小さい部屋 32 | **正しく動いている** |
| 追従（ズームアウトして追う） | 広い部屋 23 | **クランプが無い** ← 欠けているのはこれだけ |
| 自前の横追従 | 長廊下 7 | 追従＋クランプを手で実装したもの。モード2と同じ |
| ポータルの遷移カメラ | 63 | 2.4秒ブレンドを隠すための機構。不要 |

**モード2にクランプを足し、モード3をモード2に畳み、モード4を外す。** それだけです。
全部作り直す必要はありません。

クランプが無いことが、そのまま次の症状になっています。

- 広い部屋で部屋の外（暗闇・隣室）が見える
- 広い部屋でプレイヤーが画面のどこに来るか安定しない
- 長廊下だけ別実装なので、そこの境目で挙動が変わる

### ortho の統一（適用済み）

| カメラ | 変更 | 理由 |
|---|---|---|
| `CN_112` | 9.0 → **12.0** | 縦穴 20.6u に対し視野18uで見切れていた。最初の上昇の原因 |
| `CN_106` | 10.0 → **12.0** | 20.3u に対し視野20.0uで0.3u足りなかった |
| `CN_FollowCam` | 12.4 → **12.0** | エリア(12.0)との差でカットのたびにズームがポップしていた |
| `CN_LongHall_HorizontalFollow` | 12.4 → **12.0** | 同上 |

変更しなかったもの:

| カメラ | 現状 | 理由 |
|---|---|---|
| `CN_205` | 17.0 | 幅58.2uの部屋を収めるのに16.4必要。下げると見切れる |
| `CN_109` | 12.0 | **要判断**。部屋が28.7u高く視野24u。14.4に上げれば収まるが、そこだけ20%引きになる。クランプ付き縦追従にするほうが筋がよい |
| ボス / イベント / Direct | 8〜12 | 演出用。方針の対象外 |
| 広い部屋の上書き 16.0 | 5部屋 | 設計意図どおり。クランプを足す対象 |

## 11. 実装：欠けていたクランプを足した（2026-11-15）

### 追加したもの

[FollowCameraRoomClamp.cs](../Assets/Scripts/Camera/FollowCameraRoomClamp.cs) — `CinemachineExtension`。
`CN_FollowCam` に自動で付きます（`CameraManager.EnsurePlayerFollowBiasComponent` が付与）。

軸ごとに1つのルール:

```
部屋サイズ <= 視野サイズ  →  その軸は部屋の中心に固定
部屋サイズ >  視野サイズ  →  追従し、部屋の端で止まる
```

このルールだけで、今まで3つの機構に分けていた挙動が全部出ます。

|---|---|---|
| Col_105 163 x 20.3 | X追従 / Y固定 | 自前の横追従 |
| Col_109 38.8 x **28.7** | X固定 / Y追従 | 固定カメラ（見切れていた） |
| Col_210 38.9 x **80.0** | XY追従＋範囲制限 | フリー追従（**無制限**） |
| Col_112 9.0 x 20.6 | XY固定 | 固定カメラ（ortho 9 で見切れ） |

実装はパイプライン最終段で位置補正を足すだけなので、composer とも
`FollowCameraEntryFraming` とも競合しません（§15 と同じ方針）。

### 部屋の切り替わり

**クランプ矩形そのものを 0.25 秒で補間します。** カメラ位置を補間するのではないので、
プレイヤー追従は一切途切れません。調査で見つかった既知の落とし穴

> 追従中に境界を差し替えると、カメラが即座に新しい境界へクランプされてガクつく

への対処です。ただし**カメラが切り替わる場合（静止部屋↔追従部屋）は矩形を即座に差し替えます**。
カットが既に遷移なので、そこに矩形の補間を重ねると滑りが足されてしまいます。

| # | 症状（実測） | 原因 | 対応 |

### 訂正：ポータルの位置について
