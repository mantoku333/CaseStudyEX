## 0. 前の提案の訂正

`CAMERA_REWORK_ANALYSIS.md` の「案B: 固定カメラ34本をやめ、カメラ1本 + Confiner2D に寄せる」は**間違いだった**。
2つの理由で取り下げる。

### 理由1: 部屋は画面に収まっている。固定カメラは正解だった

実測し直した結果:

```
標準的な部屋のサイズ  38.3 x 20.3
OrthographicSize 12 の視野  42.7 x 24.0
```

**部屋のほうが視野より小さい。** 32部屋のうち30部屋が画面に収まりきっている。
部屋全体が一画面に入るなら、カメラを動かす意味がない。固定カメラが正しい設計で、
「部屋ごとに1枚絵」という作りはそのまま維持すべきだった。

案Bは「部屋が視野より大きい」前提で書いてしまっていた。前提が逆だった。

### 理由2: Cinemachine 自身が1本化を禁じている

`CinemachineConfiner2D.InvalidateBoundingShapeCache()` のドキュメントコメント:

> It is much more efficient to have more Cinemachine Cameras with different input bounding shapes
> and blend between them instead of changing one Confiner2D's input bounding shape and calling
> this over and over.

Confiner2D は境界形状ごとに多角形キャッシュをベイクする。1本のカメラで58部屋ぶんの
形状を差し替えると、部屋移動ごとに再ベイクが走る。Unity 側が明確に
「カメラを複数持ってブレンドしろ」と書いている。

## 1. 採用した設計

**「部屋ごとに1カメラ」は維持する。各カメラに Confiner2D を付け、境界を1つのルールで決める。**

### 唯一のルール

```
軸ごとに:
  部屋のサイズ <= 視野のサイズ  ->  Confiner がカメラをその軸で固定する
  部屋のサイズ >  視野のサイズ  ->  カメラがプレイヤーを追い、部屋の端で止まる
```

Confiner2D に渡す境界ボックス = **軸ごとに `max(部屋サイズ, 視野サイズ)`**。

これだけで、このプロジェクトにある3種類の部屋すべてが説明できる。部屋ごとのモード指定は不要。

| 部屋 | サイズ | 視野 | 結果 |
|---|---|---|---|
| 標準部屋（30個） | 38.3 x 20.3 | 42.7 x 24.0 | **XY固定** = 今の固定カメラと同じ絵 |
| 長廊下 Col_105 | 163.1 x 20.3 | 42.7 x 24.0 | **X追従 / Y固定** = 横スクロール |
| 縦長 Col_109 | 38.8 x **28.7** | 42.7 x 24.0 | **X固定 / Y追従** = 縦の見切れが消える |

固定軸ではカメラが境界ボックスの中心に落ち着くので、**境界の中心を「今の手置きカメラ位置」に取る**。
これで手で作り込んだ構図（最大1.7uのオフセット）がそのまま保存される。
実装: [RoomCameraBoundsUtility.cs](../Assets/Scripts/Camera/RoomCameraBoundsUtility.cs)

### 部屋判定のルール

旧 `FindSmallestRoomContaining()`（面積最小の部屋が勝つ）を2つのルールで置き換える。

1. **ヒステリシス** — プレイヤーが現在の部屋の端を `exitMargin` 分はっきり越えるまで、部屋を変えない。
   58部屋が65箇所で重なっていて、うち8箇所は面積差5%未満。旧ルールでは
   入っていない部屋にカメラを渡すことがあった。現在の部屋を保持すれば重なりは無害になる。

2. **一番深く入っている部屋が勝つ** — 複数の部屋に同時に属するとき、端から一番遠い部屋を選ぶ。
   面積は判定材料として不適切だった（Col_212 と Col_213 は面積差が1平方ユニット）。

実装: [RoomCameraDirector.Resolve()](../Assets/Scripts/Camera/RoomCameraDirector.cs)（純粋関数。テスト済み）

### 所有権の一本化

```
旧: RoomCameraTrigger の static 3種
      + portal hold（↑を黙らせるための機構）
      + EncounterCameraOwnership（↑2つを無視する機構）

新: RoomCameraDirector だけが Priority を上下させる
      + EncounterCameraOwnership はそのまま（Brain.SetCameraOverride を正しく使っている唯一の実装）
```

Director は **Priority の上下だけ** を行う。transform もレンズも書かない。
部屋間の動きはすべて CinemachineBrain のブレンドと各カメラの Confiner2D が生成する。

## 3. 適用手順（Unity 上で実行）

> このブランチの作業中、Unity はプロジェクトを開いたまま稼働していた。
> そのためこちらでコンパイル確認はできていない。**最初に Unity に戻ってコンパイルを通すこと。**

### 手順

1. **Unity に戻る**（フォーカスで自動インポート + コンパイルが走る）
   - コンソールにエラーが出たら、まずそれを解消する
2. `Fix_1115_CameraRework.unity` を開く
3. メニュー **`GameObject > Camera Area > Migrate Scene To Room Camera Director`** を実行
4. 完了ダイアログに出る内容を確認する
   - `RoomCameraVolume 作成: 58`
   - `カメラ複製 (共有解消): ...`
   - `Confiner2D 設定: ...`
   - `追従軸を持つ部屋:` ← 長廊下と縦長部屋がここに並ぶのが正しい
5. シーンを保存
6. 再生して確認

気に入らなければ **Ctrl+Z 一回**で戻る（Undo グループは1つにまとめてある）。

### 移行ツールがやること

- 各 `RoomCameraTrigger` から `_roomCamera` / `_horizontalFollowCamera` / `_areaColliders2D` /
  優先度を読み、`RoomCameraVolume` に移す
- **カメラを共有している部屋にはカメラの複製を作る**（Confiner2D は1カメラに1形状しか持てない）
  - 長廊下の7部屋が共有していた `CN_LongHall_HorizontalFollow` はここで分割される
  - `CN_FollowCam` は**必ず複製側を使う**。`CameraManager` が名前で解決していて、
    ストーリーとボス処理が依存しているので、元のオブジェクトには触らない
- 各カメラに Confiner2D と `CameraBounds_<部屋名>` の BoxCollider2D を生成
  - このコライダーは**形状専用**。`enabled = false` にしてある。
    Confiner2D は BoxCollider2D の `size` と transform だけを読み、`enabled` と `offset` は見ない（実装を確認済み）
- 追従軸を持つ部屋のカメラにだけ `TrackingTarget` を設定（`CN_FollowCam` の対象を流用）
- 旧ポータル5種を `enabled = false` に
- `RoomCameraTrigger` コンポーネントを除去（`MinimapRoom` は同じオブジェクトに残る）
- `CinemachineBrain.DefaultBlend` を **Cut** に（理由は §7）
- 追従軸を持つカメラの composer Damping に、旧 `_horizontalFollowSmoothTime`（0.15）を引き継ぐ
  - 旧実装は transform を手で動かしていたため composer の Damping は死に設定だった
    （長廊下カメラは 1.0 = 約7倍遅い）。移行で廊下が鈍くならないように移し替える
  - 固定軸の Damping は 0 にする（Confiner が押さえる軸に減衰を残すと原因不明の漂いになる）

## 7. 体感に関する2つの判断（2026-11-15 修正）

### 7-1. 部屋間の遷移は Cut にする。パンは「どの速さでも」間違いだった

**これは私の設計ミスだった。**

`CAMERA_SCENE_TEST_REPORT.md` で、ブレンド2.4秒 → 0.35秒 に短縮したとき、同じレポートに
こう書いていた:

```
修正後 0.35s: 隣室カメラ移動 38.0u の平均速度 108.6 u/s (プレイヤーの 15.5倍)
              ピーク速度                    162.9 u/s (プレイヤーの 23.3倍)
```

**プレイヤーの15〜23倍という数字を自分で出しておきながら、それを既定値にした。**
「2.4秒より短いなら改善」と考えて、短くした結果どんな動きになるかを見ていなかった。
移行ツールではさらに 0.25秒にしていた（= 152 u/s）。これが「ぐわん」の原因。

#### なぜ時間の調整では直らないのか

```
部屋の幅           38.3u
ortho 12 の画面幅  42.7u
→ カメラは画面幅の 90% を横断する
```

**遷移は画面のほぼ全体を入れ替える動きになる。** それを補間すると、どの時間を選んでも:

| ブレンド時間 | カメラ速度 | 体感 |
|---|---|---|
| 2.4s | 15.8 u/s | 自分より2.3倍速い画面が2.4秒流れ続ける = 酔う |
| 0.5s | 76 u/s | 画面1.8枚分/秒 = 速いパン |
| 0.35s | 109 u/s | 画面2.5枚分/秒 = ぐわん |
| 0.25s | 152 u/s | 画面3.6枚分/秒 = 鞭 |

**遅い＝漂流、速い＝鞭。ちょうどいい値は存在しない。** 問題は速度ではなく、
「画面9割を横に掃く動き自体」だった。

#### Cut が正解である理由

動きをなくせば、酔いも鞭もない。`Style: Cut` は視線が新しい静止画に即座に再定着する。

部屋ごとに固定カメラを置く設計（＝ゼルダ／メトロイド型）で、これは例外ではなく標準。
**「部屋ごとに1枚絵」を選んだ時点で、遷移はカットが自然な帰結だった。**
2.4秒のブレンドは、その設計に合わない設定が最初から入っていただけ。

副作用として、カット時にプレイヤーの画面内位置が左右に飛ぶ。
部屋が変わったことが一目で分かるので、この設計では意図された挙動になる。

#### それでもパンにしたい場合

パンが成立するのは「隣のカメラが近い」場合だけ。そのためには
**部屋より視野を小さくする**（ortho 12 → 9.5 以下）必要がある。
そうすると全部屋が追従カメラになり、継ぎ目でのカメラ間距離がほぼ0になるのでパンが自然になる。

ただしこれは画面の見え方が26%拡大する**アートディレクションの変更**なので、こちらで決めるべきではない。
やるなら別検討。

`CinemachineBlenderSettings` を作れば「部屋↔部屋はCut、追従部屋↔固定部屋は短いブレンド」と
ペアごとに分けられる。カットの飛びが気になる箇所が出たらこれで個別対応する。

### 7-2. 廊下の上下ロックは、元の実装が正しかった

**ご指摘のとおり。これも私が壊した。**

`CAMERA_SCENE_TEST_REPORT.md` の修正2で、長廊下7部屋を
`_useHorizontalFollowCameraWhenEntered: 1 → 0` にして通常の `_roomCamera` 経路に変えた。
その結果 `CinemachinePositionComposer` が有効になり、**X だけでなく Y も追従するようになった。**

旧実装 [RoomCameraTrigger.cs:522](../Assets/Scripts/Camera/RoomCameraTrigger.cs:522) は
明確に Y を固定していた:

```csharp
currentPosition.x = Mathf.SmoothDamp(...);   // X は追従
currentPosition.y = targetPosition.y;        // Y は部屋中心に固定
```

私はこの `transform` 直書きを「Cinemachine と戦っている」と判断して経路ごと外したが、
**Y固定という意図まで一緒に捨ててしまった。** 書き方は問題だったが、仕様は正しかった。

#### どちらが良いか：Y固定が正しい

```
廊下の高さ        20.3u
ortho 12.4 の画面高  24.8u
→ 廊下の高さは画面に収まりきっている
```

**上下に動かしても、廊下の外（暗闇）が映るだけで得るものがない。**
一方で失うものは大きい:

- ジャンプ（jumpForce 3.2）するたびに画面が縦に揺れる
- 不感帯 0.1212 × 24.8 = 3.0u しかないので、ちょっとした段差でも反応する
- 横に走りながら縦に揺れる = 2軸同時の揺れで最も酔いやすい

縦に追従する価値があるのは、**部屋の高さが画面より大きいとき**だけ。
Col_109（28.7u > 24.8u）や Col_112（20.6u > 18.0u）がその該当例で、
そこでは逆に今プレイヤーが画面外に出ている。

つまり §1 の「軸ごとに `max(部屋サイズ, 視野サイズ)`」というルールが、
**まさにこの判断を自動でやる。** 廊下は Y固定、Col_109 は Y追従。
ルールの方は最初から正しかったので、変更は不要。

#### 現在のシーンの状態

長廊下6部屋（Col_102 / 105 / 107 / 301 / 311 / 321）は**元の Y固定実装に戻した。**
元シーンからの差分は7行だけになっている:

| 変更 | 理由 |
|---|---|
| `DefaultBlend`: EaseInOut 2.4s → **Cut** | §7-1 |
| 4部屋の `_useDefaultCameraWhenEntered` 1 → 0 | フラグ二重ONの解消（挙動が経路依存だった） |
| `Col_322` の `_useHorizontalFollowCameraWhenEntered` 1 → 0 | 専用カメラ `CN_322` が使われていなかった |

**残っている既知の問題**: 長廊下6部屋は1本のカメラを共有したままなので、
離れた廊下へ入り直すと最大837uの横滑りが起きる（`CAMERA_SCENE_TEST_REPORT.md` §2）。
これを消すには移行ツールの実行が必要で、移行後は
**カメラ分割 + Confiner による Y固定**の両方が同時に満たされる。

## 8. エリア間の往復で「ぐわんぐわん」する問題（2026-11-15 追加）

### 原因：ヒステリシスの不感帯が片側しかなかった

`exitMargin`（0.5）は「現在の部屋から出る条件」だけを定めていた。
入る側の条件は「部屋に含まれていればよい」だった。その結果:

```
Col_101  x ∈ [-19.15, 19.15]
Col_102  x ∈ [ 19.15, 57.45]   （境界を共有）

x = 19.65 で 101 を出る（0.5u 外）  -> 102 へ
x = 18.65 で 102 を出る（0.5u 外）  -> 101 へ
→ 反転帯は わずか 1.0u
```

プレイヤーは 7 u/s なので、**1.0u の帯を 0.14秒で横切る。**
つまり境界付近で左右に歩くと **0.14秒ごとに 38u の視点移動**が起きていた。これが「ぐわんぐわん」。

ブレンドを Cut にしても、点滅のように画面が入れ替わるだけで解決しない。
**ブレンド設定の問題ではなく、部屋判定の不感帯の問題だった。**

### 対策1：入る側にも敷居を設けた（`enterDepth` = 3u）

新しい部屋がカメラを取るには、**プレイヤーがその部屋に 3u 入っている**ことを要求する。

```
反転帯  1.0u  ->  約 6.9u（exitMargin + enterDepth が両側に効く）
```

細い部屋（幅が 2 × enterDepth 未満）は 3u の深さに到達できないため、
`min(enterDepth, 部屋の短辺の半分 × 0.5)` に自動で緩める。
これがないと細い部屋が永久にアクティブにならない。

テスト: `WalkingBackAndForthOverABoundary_DoesNotKeepFlippingTheCamera`
`ThinRoom_CanStillTakeTheCamera_DespiteTheEnterDepthRequirement`

### 対策2：切り替えの最小間隔（`minHoldSeconds` = 0.3秒）

不感帯だけでは、本気で往復するプレイヤーは止められない。
部屋が変わってから 0.3秒は次の変更を受け付けない。

例外は3つ:
- `RoomCameraEarlySwitch` などの明示的な要求（意図的な操作なので絞らない）
- 起動直後（`activeRoom == null`）
- **同じカメラを使う部屋どうしの移動**（見た目が変わらないので絞る意味がない）

時間は `Time.unscaledTime`。会話中に時間が止まっていても遷移が完了する。

### 対策3（本命・任意）：継ぎ目そのものを無くす

対策1・2は**緩和**であって除去ではない。完全に無くす方法は
**隣り合う部屋に同じカメラと同じ境界コライダーを割り当てる**こと。

同じカメラを共有していると、`RoomCameraDirector.Commit()` は
Priority を下げてから上げるのを同一フレーム内で行い（`[DefaultExecutionOrder(-50)]` により
`CinemachineBrain` より先に走る）、**Brain からはカメラが切り替わったように見えない。**
結果、カメラはアクティブのまま X 追従を続け、**視点の飛びも反転も原理的に起きない。**

**新しいコードは不要。** Inspector で2つのフィールドを合わせるだけ:

```
Col_101 / Col_102 / Col_103 の RoomCameraVolume
    Room Camera      = 同じカメラ（例 CN_101）
    Confiner Bounds  = 同じ境界（3部屋を覆う 152.3 x 24.0 のボックス）
```

境界は §1 のルールどおり「軸ごとに `max(連なりのサイズ, 視野サイズ)`」。
152.3 x 20.6 の連なりなら **X追従 / Y固定** になる。

シーンを調べたところ、水平につながった部屋の連なりが見つかっている:

| 連なり | 全体サイズ | 消える切り替え |
|---|---|---|
| 107-108-109-111 | 236.0 x 58.6 | 3箇所 |
| 323-322-321-320 | 152.0 x 20.7 | 3箇所 |
| 101-102-103 | 152.3 x 20.6 | 2箇所 |
| 217-218-219 | 94.5 x 21.8 | 2箇所 |
| 201-202 / 205-206 / 212-213 / 304-305 / 306-307 / 308-309 / 314-315 / 215-214 / 105-106 | 各 75〜176 | 各1箇所 |

**合計19箇所の切り替えが消える**（32部屋が13の連なりに入る）。

#### ただしこれはアートディレクションの変更

連なりにまとめると、その区間は「部屋ごとの1枚絵」ではなく**横スクロール**になる。
34本の手置きカメラで作った構図のうち、まとめた区間ぶんは失われる。

長廊下（Col_105 など）は元々そう作ってあったので違和感はないはずだが、
標準部屋を連ねるかどうかは**見せ方の判断**なので、こちらでは決めない。

**推奨**: まず対策1・2（適用済み）で走ってみて、それでも気になる継ぎ目があれば
**その継ぎ目だけ**連なりにまとめる。全部まとめる必要はない。

### 調整値

|---|---|---|
| `RoomCameraDirector.exitMargin` | 0.5 | 部屋から出にくくなる |
| `RoomCameraDirector.enterDepth` | 3.0 | 部屋に入ってから切り替わるまでが深くなる（反転しにくい） |
| `RoomCameraDirector.minHoldSeconds` | 0.3 | 連続切り替えの上限間隔が伸びる |

落下が速い縦ルートで切り替えが遅れて感じる場合は `minHoldSeconds` を下げる。

### 9-1 / 9-4：切り替え位置と頻度（修正済）

旧 `ValidateActiveRoomAgainstPlayer()` は「コライダーに入った瞬間」に切り替え、
判定は「面積最小の部屋」でした。隣室は辺を共有しているので**反転帯は実質0u**。

`RoomCameraTrigger` に3つのパラメータを追加し、判定を入れ替えました。

| フィールド | 既定 | 効果 |
|---|---|---|
| `_roomExitMargin` | 0.5 | この距離だけ外に出るまで現在の部屋を保持 |
| `_roomEnterDepth` | 3.0 | 新しい部屋に3u入るまで切り替えない（細い部屋は自動で緩和） |
| `_roomMinHoldSeconds` | 0.3 | **直前に出た部屋へ戻る場合のみ**抑制 |

判定も `FindSmallestRoomContaining`（面積最小）から `FindDeepestRoomContaining`（端から一番遠い）へ。
Col_212 と Col_213 は面積差1平方ユニットで、どちらが勝つか事実上ランダムでした。

**重要**：最小間隔は「戻る場合だけ」に限定しています。一律にすると落下で破綻します（§9-6）。
また `TryActivateRoomAtPosition`（ワープ・ストーリー・ボス入場）は従来どおり即座に切り替わります。

部屋の隙間で現在の部屋を保持するようにもしました。従来は隙間に入るとフォローカメラへ落ちて
すぐ戻る、という目に見える跳びが出ていました。

### 9-2：切り替え後にプレイヤーを見失う（要判断）

カット前はプレイヤーが部屋Aの視野の右端、カット後は部屋Bの視野の左端にいます。
**画面内の位置が約38u＝ほぼ1画面分飛ぶ**ので、目が追えません。

カットのタイミングを変えても直りません。飛ぶ量はカメラ間距離で決まっています。
消すには距離をなくすしかなく、方法は§8-3と同じ3つです。

1. 隣接部屋を連なりにまとめる（その区間は切り替えが起きない）
2. ortho を下げて全部屋を追従カメラにする
3. カットを一瞬の暗転で隠す（新規実装が必要）

### 9-3：Fog（原因特定済・未変更）

```
Assets/Prefabs/RoomFogRevealManager.prefab
    revealDuration:  1.6   ← 霧が晴れるまで
    concealDuration: 1.8   ← 霧が戻るまで
```

`RoomFogRevealManager` は `RoomCameraTrigger.ActiveRoomChanged` を購読しています。
**カメラが0秒で切り替わる一方、Fogは1.6〜1.8秒かけるため、到着した部屋がしばらく暗く、
出た部屋の霧が残って見えます。** これが「遅い・変・残ってる」の正体です。

元の2.4秒ブレンドとは 1.6秒がほぼ釣り合っていたので、**私がカットにした時点でこの対応が崩れました。**

カットに合わせるなら 0.3〜0.4秒程度が妥当です。ただしこのprefabは**全シーン共有**で、
未移行のシーンはまだ2.4秒ブレンドなので、変更するとそちらが逆に合わなくなります。
そのため**こちらでは変更していません。**

### 9-5：見切れ

Col_112（9.0 x **20.6** / 視野18.0）と Col_109（38.8 x **28.7** / 視野24.0）は
部屋が視野より高く、上下に動くと確実に画面外に出ます。
他の31/32本も部屋の外を2u以上映しています。

どちらも Confiner2D で構造的に解決します（§1のルールが Col_109 を自動でY追従にする）。
移行ツール実行まで有効になりません。

### 9-6：上下移動が特に悪い理由

```
Player.prefab  m_GravityScale: 2   →  実効重力 19.62
部屋の高さ 20.3u を落ちる時間 = √(2×20.3/19.62) = 1.44秒
到達速度 = 19.62 × 1.44 ≒ 28 u/s
```

**落下は走行（7 u/s）の約4倍の速さ**です。縦のカメラ間距離20.5uは視野高24uの85%なので、
横と同じ割合の飛びが4倍の頻度で、しかも着地点を見たい場面で起きます。

この数字があるため、最小間隔を一律0.3秒にするのは危険です
（28 u/s × 0.3s = 8.5u ＝ 部屋の高さの4割）。だから「戻る場合のみ」に限定しました。

縦の飛びそのものは§9-2と同じ対策が必要です。

### 9-7：自由カメラへの遷移（修正済）

順序が逆でした。

```
旧: SwitchToFollowCamera()         ← Priorityを上げる（＝ここでカットが起きる）
    ApplyDefaultFollowCameraOverrides()  ← その後にズームとオフセットを書く
```

カメラは非アクティブ中も前の姿勢を保持し、body の damping は1.0秒です。
そのため**古い姿勢と古いレンズにカットしてから、damping で所定位置へ滑る**という
二段階になっていました。これが「ガクッ」です。

修正後は、構図を書く → body をスナップ → Priority を上げる、の順にしました。

- `CameraManager.SnapFollowCameraToTarget()` を追加。`PreviousStateIsValid = false` で
  1評価ぶん damping を飛ばし、目標位置に正確に着地させます
- `FollowCameraFacingBias.ResetSmoothing()` を追加。前の部屋で落下中に溜まった
  先読みオフセット（`verticalOffsetSmoothTime` 0.4秒）がカット後に戻っていくのを止めます

これで自由カメラへの遷移もエリア間と同じ「完成した1フレームへの切り替え」になります。

### 移行前に直した不具合

移行ツールが `RoomCameraTrigger` を**削除**する実装になっていました。これは壊れます。
この型は3つのシステムが部屋IDとして使っていました。

| 利用側 | 用途 |
|---|---|
| `RoomFogRevealManager` | 1,972行すべてが `RoomCameraTrigger` を部屋型として使用 |

削除すれば **Fog・敵活動・ストーリーの部屋復帰が静かに壊れていました。**

対応：`RoomCameraTrigger` は残し、`ExternalCameraAuthority` でカメラ制御の半分だけ無効化。
`RoomCameraDirector` は `SetActiveRoomExternally()` で同じ `ActiveRoomChanged` に
部屋変更を再発行するので、3システムは無改造で動き続けます。

### 9-3 再追記：Fog を無効化しました。チカチカの原因は時間ではなくフレーム順序

#### 原因：マスクがカメラより1フレーム遅れている

```
RoomFogRevealManager.Update()        ← 霧マスクを塗る（FlushDirtyMasks）
RoomCameraTrigger.LateUpdate()       ← 部屋が切り替わる
CinemachineBrain                     ← カメラがカットする
```

部屋の切り替えは **LateUpdate**、霧マスクの塗り直しは **Update** です。つまり:

```
フレームN   : Update で「前の部屋」のマスクを塗る
              → LateUpdate で部屋が変わり、カメラがカットする
              → このフレームは「新しい部屋 ＋ 前の部屋のマスク」で描画される
                 = 新しい部屋が完全に霧で覆われた1フレーム  ← これが一瞬の暗さ
フレームN+1 : ようやく新しい部屋のマスクが塗られ、reveal が始まる
```

**`revealDuration` をいくら短くしてもこの1フレームは消えません。** 0.3秒にしても、
最初の1フレームは真っ暗なままです。2.4秒ブレンドの頃はカメラがゆっくり動いていたので
この暗転がパンに紛れていましたが、カットにしたことで露出しました。

#### 対応：`fogEnabled: 0`

```
Assets/Prefabs/RoomFogRevealManager.prefab
    fogEnabled: 1  ->  0
```

**1つの値なので、戻すのも一瞬です。** `revealDuration` / `concealDuration` は
カットに合わせた値（0.3 / 0.35）のまま残してあるので、再有効化するなら釣り合った状態から始まります。

#### 知っておくべき副作用：Fog は別の不具合を隠していました

`CAMERA_SCENE_TEST_REPORT.md` §4 の通り、固定カメラ32本のうち **31本が部屋の外を2u以上映しています**。

| 部屋 | 部屋の外を映す量 |
|---|---|
| Col_106 | **12.5u**（画面の2/3が部屋の外） |
| Col_112 | **12.3u** |
| Col_205 | 縦 7.5u |

**Fog はこの「隣室や暗闇が見えてしまう」状態を覆い隠す役もしていました。**
無効化すると、そこが素で見えるようになります。

これを構造的に直すのが Confiner2D です（§1のルールでカメラが部屋の外を映さなくなる）。
移行後は、Fog は純粋に演出として入れるか切るかを選べる状態になります。

#### Fog を残したい場合の直し方

演出として残したいなら、時間ではなく順序を直す必要があります。

1. `SetCurrentRoom()` の中で `FlushDirtyMasks()` を同フレームに呼び、
   マスクを部屋切り替えと同じフレームで確定させる
2. あるいは霧の毎フレーム処理を `Update()` から `LateUpdate()` に移し、
   部屋判定より後の実行順にする

どちらも 1,972行のファイルへの変更になるので、Fog を使うと決めてから着手するのが妥当です。

### 9-3 訂正：Fog は再有効化し、チカチカを直しました

**`fogEnabled: 0` にしたのは誤りでした。** Fog は演出だけでなく、
固定カメラ32本のうち31本が部屋の外を映している状態を覆い隠す役も担っています。
切れば演出も遮蔽も失われ、別の問題に置き換えただけでした。`fogEnabled: 1` に戻しました。

チカチカは2つの独立した原因の合成で、どちらも直せるものでした。

#### 原因1：入った部屋の reveal が「完全な霧」から始まる

`ResolveRoomVisibility()` は、まだ入っていない部屋には 0 を返します。
そのため新しい部屋に入ると毎回フル reveal が再生されます。
2.4秒ブレンドの頃はカメラが動いている裏で進行していたので見えませんでしたが、
カットにしたことで「暗→明」が露出しました。

対応：`revealInstantlyOnRoomChange`（既定 on）を追加。
部屋が切り替わったときは入った部屋を**最初から晴れている**ものとして扱います。
出た部屋の conceal は従来どおり動くので、演出は保たれます。
`RevealRoom()` の明示呼び出し（`restartEvenIfSame`）は従来どおりフル再生します。

#### 原因2：マスクがカメラより1フレーム遅れる

```
RoomFogRevealManager.Update()     ← マスクを塗る
RoomCameraTrigger.LateUpdate()    ← 部屋が切り替わり、カメラがカットする
```

カットしたフレームは「前フレームのマスク」で描画されるので、
入った部屋が完全な霧で1フレーム表示されます。`revealDuration` を何秒にしても残ります。

対応：`SetCurrentRoom()` の末尾で `FlushMasksNow()` を呼び、
部屋切り替えと同じフレームでマスクを確定させます。

#### 結果

| | 変更前 | 変更後 |
|---|---|---|
| `fogEnabled` | 1 → 0（誤り） | **1** |
| 入室時の reveal | 完全な霧から0.3秒 | **最初から晴れている** |
| マスク更新 | 1フレーム遅れ | **同フレーム** |
| 退室時の conceal | 0.35秒 | 0.35秒（変更なし） |

## 10. かくつき2回と「急すぎる」の調査結果（2026-11-15）

### 10-1. エリア ↔ フリー で2回かくつく原因

`FollowCameraFacingBias` が**カメラの追従対象を差し替えている**のが前提です。

```csharp
// EnsureLookAheadTrackingTarget()
GameObject targetObject = new GameObject("FollowCameraDownwardLookAheadTarget");
lookAheadTrackingTarget.SetParent(sourceTrackingTarget, false);
followCamera.Target.TrackingTarget = lookAheadTrackingTarget;   // ← プロキシに差し替え
```

CN_FollowCam はプレイヤーではなく、この**プロキシ**を追っています。そして毎フレーム
プロキシを最大 `fallingLookAheadOffsetY`（3u）下にずらし、composer の
`TargetOffset.x` を facing に応じて ±2.25u 書き換えます。

かくつきはこの**2つのオフセットに対応していました**。

| # | 原因 | ずれ量 |
|---|---|---|
| 1 | プロキシ位置が前の部屋の値のまま。カットでそこに吸着し、次フレームでプロキシが0に飛ぶ | 最大 **3u** 縦 |
| 2 | `TargetOffset.x` は `Update()` で書かれる＝カットの後。その後 Damping 1.0 で寄っていく | 最大 **2.25u** 横 |

前回の `ResetSmoothing()` は `currentDownwardCameraOffset` の**変数だけ**0にして、
**プロキシの transform を動かしていませんでした。** だから残っていました。

#### 3つめ：実行順が未定義だった

`RoomCameraTrigger.LateUpdate`（部屋判定）と `CinemachineBrain.LateUpdate`（ブレンド）は
どちらも LateUpdate で、**Brain は `DefaultExecutionOrder` を宣言していません**。
つまり順序が未定義で、Brain が先に走ったフレームは
「部屋はもう変わっているのに前の部屋のカメラで描画」になります。
これは**両方向**で起きるので、フリー→エリアでもかくついていた説明になります。

#### 対応

- `ResetSmoothing()` を `Apply(instant: true)` に変更。
  プロキシ位置と composer オフセットを**その場で最終値にする**（SmoothDamp を通さない）
- `RoomCameraTrigger` に `[DefaultExecutionOrder(-50)]` を付与。Brain より確実に先に走る

### 10-2. 「切り替えが急すぎる」＝ 時間では解けない

これまでに試した値の評価:

| ブレンド | 評価 |
|---|---|
| EaseInOut 2.4s | 酔う |
| EaseInOut 0.35s | ぐわん |
| **Cut** | **急すぎて違和感** |

**全域が否定されました。** つまり調整すべき変数は時間ではありません。
原因はカメラ間の**38u（画面幅の90%）という距離**です。

#### 対応：継ぎ目そのものを消す「カメラ連なり」

隣り合う部屋に**同じ追従カメラ＋同じクランプ範囲**を割り当てると、
部屋をまたいでも**カメラオブジェクトが変わらない**ので、
Cinemachine から見て遷移が存在しません。カメラはただプレイヤーを追い続けます。

実装:

| 追加 | 内容 |
|---|---|
| `RoomCameraTrigger._horizontalFollowClampBounds` | クランプと縦中心を、部屋ではなく連なり全体の形状で決める |
| `ActivateHorizontalFollowCamera()` の分岐 | 同じカメラの部屋へ移る時は `horizontalFollowVelocityX` を引き継ぎ、追従を再開始しない（しないと継ぎ目ごとに一瞬停まる） |
| `Assets/Editor/CameraRunSetup.cs` | `GameObject > Camera Area > Make Camera Run From Selection` |

ツールは選択した部屋から連なりカメラとクランプ形状を生成し、全部屋に割り当てます。
実行前に「連なりが画面より高いのでYが固定できない」等の警告を出します。

## 13. 画面内のプレイヤー位置が変わる件の検討と対応

### 問題

エリアカメラは静止しているので、プレイヤーは画面のどこにでもいます（部屋の端にいれば画面の端）。
フリーカメラはプレイヤーを決まった画面位置に保ちます。
**カット時にプレイヤーが画面を横断して移動する**ので、カット自体は一瞬でも違和感が残ります。

### 検討した選択肢

| 案 | 内容 | 判定 |
|---|---|---|
| A | 2つのカメラ位置をブレンド | ✗ 既に却下したパンと同じ。しかもプレイヤーは結局画面を横断する |
| B | **カット時の画面内位置を引き継ぎ、構図へ寄せる** | **採用** |
| C | エリアカメラ側の構図を合わせる | ✗ 静止カメラでは部屋内でプレイヤーが動くので不可能 |
| D | 全部屋を追従カメラにする | △ 正しいが、視野より小さい部屋は追従できないので結局揃わない |
| E | フリーカメラが引き継いだ位置のまま使う | ✗ 構図が永久に戻らない |

### 採用案B の仕組み

`FollowCameraEntryFraming.cs`

1. カットの瞬間、composer の `ScreenPosition` を「プレイヤーが今映っている画面位置」に設定する
   → 新カメラの位置が**旧カメラの位置と一致**するので、**カットで絵が一切変わらない**
2. その後 `settleSeconds`（既定0.45秒）かけて `ScreenPosition` を本来の構図へ ease
   → 世界がゆっくり寄っていき、**目が追っているプレイヤーは動かない**

副次的に、`matchOutgoingLens` で ortho（エリア12.0 / フリー12.4）も揃えてから戻すので
ズームのポップも消えます。ease 中は dead zone を切って干渉を防ぎます。

**プレイヤーが画面内で飛ばない＝「見失う」問題にも同時に効きます。**

## 14. 訂正：ポータルを消したのは誤りだった（2026-11-15）

Fog を切った時と**同じ誤り**を繰り返していました。壊れている部分だけを外すのではなく、
機能ごと無効化して症状を消していました。

### ポータルが担っていた2つの仕事

| 仕事 | 判定 |
|---|---|
| 優先度30の遷移カメラを自前 SmoothDamp で動かす | **本当に不要**。2.4秒ブレンドを隠すための機構で、Cut では2回のガクつきを生むだけ |
| **どこで切り替えるかという位置情報** | **必要**。手で置かれた設計情報で、代わりがなかった |

### 位置情報であることの実測

43本の `RoomCameraPortal` について、ポータルの中心と「部屋Aと部屋Bの幾何的な境界」の距離を測定:

| | 値 |
|---|---|
| ズレ 中央値 | **6.1u** |
| ズレ 最大 | 24.5u（Portal_107_109） |
| ズレ2u超 | **43本中40本** |
| サイズ 中央値 | 3.8u × 6〜7u |

部屋の高さは約20uなので、高さ6〜7uのコライダーは**ドア口**です。
幾何的な境界から中央6uズラした位置に、3.8u幅で置かれている。これは偶然ではなく配置の意図です。

### なぜこれが「急すぎる」に直結するか

ヒステリシス（`_roomExitMargin` / `_roomEnterDepth`）が置き換えたのは
「出口でない壁際で切り替わらないこと」だけです。
**「ドア口で切り替えること」は置き換えていませんでした。**

ポータルを消すと、切り替わる場所は部屋コライダーが重なった位置で決まります。
§9-5 で測ったとおり、その重なりは部屋の全幅にわたる帯であることが多く、
つまり**何もない床の真ん中でカットが起きる**。
ドア口で切れば意図的に見え、床の真ん中で切れば不具合に見えます。

### 対応：遷移カメラだけを外し、位置は戻す

`RoomCameraPortal` と `VerticalRoomCameraPortal` に `useTransitionCamera` を追加（既定 off）。

```csharp
if (!useTransitionCamera)
{
    // 切り替え位置を示すだけ。プレビューカメラも補間も行わない。
    TryCommitFullyEnteredRoom();
    return;
}
```

既存のシリアライズ値にこのフィールドは無いので、**43本すべてが自動的に off** になります。
そのうえでシーンの53本を再有効化しました。

| 種類 | 数 | 状態 |
|---|---|---|
| `RoomCameraPortal` | 43 | **再有効化**（遷移カメラのみ無効） |
| `VerticalRoomCameraPortal` | 4 | **再有効化**（同上） |
| `FallRoomCameraPortal` | 6 | **再有効化**（元々遷移カメラを持たない） |
| `RoomCameraSwitchPortal` | 10 | 有効のまま |

これで「ドア口で切り替わる」は戻り、「2回ガクつく」原因だけが消えます。

### 教訓

症状が出ている機能を丸ごと止めるのは、原因の切り分けであって修正ではありません。
Fog でも同じことをしました。**止める前に、その機能が他に何を担っているかを測ること。**

## 15. 訂正：FollowCameraEntryFraming の実装をやり直した（2026-11-15）

初版は composer の `Composition.ScreenPosition` を毎フレーム書き換えていました。
これは3つの仕組みと同時に衝突します。

| 相手 | 衝突内容 |
|---|---|
| `HardLimits` (0.8 × 0.8 → 半径0.4) | ScreenPosition を最大±0.75まで振るので、範囲外に出た瞬間に毎フレーム引き戻される |
| composer の `Damping` (1,1,1) | 0.45秒の ease の上に1秒の減衰が重なり、2つの動きが同時進行 |
| 部屋ごとのズーム上書き | 毎フレーム `cam.Lens` を書くので、`RoomCameraTrigger` が直前に適用した ortho を上書き |

特に1つ目は毎フレームの引っ張り合いになります。

### 書き直した方式

`CinemachineExtension` にして、パイプライン最終段で**減衰する位置補正を足すだけ**にしました。

```csharp
protected override void PostPipelineStageCallback(..., ref CameraState state, ...)
{
    if (stage != CinemachineCore.Stage.Finalize) return;
    // 初回: 旧カメラ位置と本来の解との差を取る
    // 以降: その差を settleSeconds かけて 0 に近づける
    state.PositionCorrection += entryOffset * weight;
    state.Lens.OrthographicSize += entryOrthographicDelta * weight;
}
```

- 切り替わった瞬間、カメラが旧カメラ位置に一致 → **絵が変わらない**
- 0.5秒かけてズレが0になる → 本来の構図まで歩く

パイプラインの後段に足すだけなので、`HardLimits` とも damping ともレンズ上書きとも
**構造的に衝突しません**。`PreviousStateIsValid = false` を併用して、
本体の減衰と二重に動かないようにしています。

`state.Lens.Orthographic` での分岐は使っていません。これは `ModeOverride` を読む実装で、
このシーンでは `None` のためズーム補間が無言でスキップされます。
両方の ortho が正であることを条件にしています。

### 教訓（§14 と同根）

composer のような既存の調停機構を外から書き換えると、その機構が持つ制約
（ハードリミット、減衰、他所からの上書き）と必ず競合します。
**足すなら、調停が終わった後ろに足す。**
