# パフォーマンスチューニング計画書

## 目的

本計画は、`UnityPerformanceTuningBible_JP.pdf` のワークフローを、このプロジェクトで再現可能な改善プロセスに落とし込むためのものです。推測や慣習だけで変更せず、実機・実ビルドの計測結果からボトルネックを一つずつ解消します。

対象はフレームレート低下、フレーム時間のスパイク、メモリ使用量・リーク、ロード時間、およびビルドサイズです。最初の改善対象は、リリースに使用するシーンと、最も負荷の高いゲームプレイ・演出を含むシーンとします。

## 前提と現状

- Unity `6000.3.8f1`、URP `17.3.0`、2D テンプレートをベースにしたプロジェクトである。
- 有効なビルドシーンは `Assets/Scenes/FixScenes/Title.unity` と `Assets/Scenes/FixScenes/Fix_CAPCOM.unity` である。
- Android の設定は存在する一方、性能保証対象のプラットフォーム・端末・画質水準は未確定である。そのため、Phase 0 で確定するまで数値目標を固定しない。
- `QualitySettings` は既定で `Very Low`、複数の品質段階を持つ。品質設定を変える施策は、画質仕様とセットで判断する。
- `Update` / `FixedUpdate` / `LateUpdate` を持つスクリプトは89本ある。特に敵・ボス・エフェクト・部屋フォグ・UI・2D 物理を、計測後の重点調査候補とする。

本PDFは Unity 2020.3・スマートフォンを主な前提にしているため、原則（計測して切り分けること）は採用し、Unity 6 / URP の設定名・挙動は実プロジェクトと現行ドキュメントで確認してから変更する。

## 成功条件

Phase 0 で次の表を埋め、合意済みの値を完了条件とする。フレーム時間は FPS ではなく ms で管理し、平均値だけでなく P95/P99 と最大値も確認する。

| 指標 | 目標値 | 計測条件 | 判定 |
| --- | --- | --- | --- |
| 平均 / P95 / P99 フレーム時間 | 未確定 | 指定シーン・指定操作を各3回以上 | 目標以下 |
| 最大フレーム時間（スパイク） | 未確定 | 戦闘、敵出現、演出、遷移を含む | 目標以下 |
| CPU / GPU フレーム時間 | 未確定 | 実機または性能保証PC | 片方が予算を恒常的に超えない |
| GC Alloc / frame と GC スパイク | 未確定 | 高負荷ゲームプレイ | 継続的な不要割当なし、スパイクなし |
| ピークメモリ / シーン遷移後メモリ | 未確定 | 起動から代表シナリオ完走 | 上限内、遷移反復で増加しない |
| 起動・シーン遷移時間 | 未確定 | コールド起動、遷移各3回 | 目標以下 |
| ビルドサイズ | 未確定 | Release相当ビルド | 配布上限内 |

## 対象シナリオ

計測ごとに操作、時間、設定、ビルドを固定する。まず下記を基準にし、Phase 0 で再現性を確認する。

| ID | シナリオ | 主な観測対象 |
| --- | --- | --- |
| S1 | タイトル起動からゲーム開始まで | 起動・ロード、常駐メモリ、初期化時スパイク |
| S2 | `Fix_CAPCOM` を通常移動・カメラ移動しながら3分間プレイ | 定常CPU/GPU、描画、2D物理、フォグ・背景 |
| S3 | 敵が多い区画で戦闘・被弾・撃破を繰り返す | `Instantiate`/`Destroy`、GC、物理、エフェクト |
| S4 | ボス戦または最も重い演出を開始から終了まで実行 | フレームスパイク、弾・演出、UI、描画 |
| S5 | タイトル⇔ゲームプレイの遷移を10回繰り返す | メモリリーク、未解放アセット、遷移時間 |

実機が未指定の場合は、まず開発PCの Release 相当ビルドで傾向を取る。ただし最終判定は性能保証対象の端末で行い、Editor 上の数値だけで完了としない。

## 実行計画

### Phase 0: 目標・計測条件の確定（0.5〜1日）

1. 配布先（Windows / Android / iOS）、最低保証端末または最低保証PC、目標FPS、解像度、品質設定、許容する画質劣化を決める。
2. 上記「成功条件」の目標値と、S1〜S5 の実行手順を合意する。
3. 計測用ビルドの設定を記録する。Development Build、Autoconnect Profiler、Deep Profiling、Script Debugging は必要な計測だけで切り替え、比較対象どうしでは同じ条件にする。
4. バージョン、コミット、端末OS、解像度、品質設定、温度・電源状態、VSync / target frame rate を記録する。

**成果物:** 性能予算表、端末マトリクス、再現手順書、計測条件テンプレート。

### Phase 1: ベースライン計測（1〜2日）

1. S1〜S5 を各3回以上実行し、Unity Profiler の CPU Usage、Rendering、Memory、GC Alloc、Physics を取得する。
2. Profile Analyzer で各シナリオの中央値、P95、P99、最悪フレームを集計する。
3. スパイク時は該当フレームの Hierarchy / Timeline を保存し、原因候補を「メソッド名・呼び出し元・発生回数・ms・Alloc」で記録する。
4. Memory Profiler で、起動直後・高負荷中・遷移10回後のスナップショットを取得する。差分で増え続ける Native / Managed / Graphics メモリと参照元を確認する。
5. GPU負荷が疑われる場面だけ Frame Debugger を使い、描画イベント、マテリアル切替、半透明の重なり、UI再描画を確認する。

**成果物:** `outputs` または `ProfilerCaptures` 配下の生データ、ベースライン結果表、課題バックログ。

### Phase 2: 原因の切り分けと優先順位付け（0.5〜1日）

PDF第1章に従い、発見事項を次の分類に分ける。ひとつの問題に対して複数の最適化を同時に入れない。

| 症状 | 最初に確認すること | 主なツール | 次の調査 |
| --- | --- | --- | --- |
| 一時的なカクつき | GCか、特定処理・ロード・描画の急増か | Profiler / Profile Analyzer | 割当元、同期処理、生成・破棄、演出の集中 |
| 常時遅い | CPU boundかGPU boundか | Profiler / 実機GPU計測 | CPUならスクリプト・物理、GPUなら描画・解像度 |
| メモリが増え続ける | シーン遷移・同じ演出の反復で差分が増えるか | Memory Profiler | 参照保持、イベント解除漏れ、未解放の実体 |
| メモリが最初から大きい | 最大アセット・テクスチャ・AudioClip・メッシュは何か | Memory Profiler / Import設定 | 圧縮、解像度、ロード・アンロード方針 |
| ロードが遅い | Main Thread、I/O、デシリアライズのどれか | Profiler | 分割ロード、先読み、アセット構成 |

優先度は「性能予算の超過量 × 発生頻度 × プレイ影響 ÷ 改修リスク」で決める。安全性・進行不能・クラッシュにつながる項目は、この計算によらず最優先にする。

**成果物:** 原因が計測で裏付けられた優先順位付きバックログ。各項目には、再現シナリオ、根拠キャプチャ、期待効果、リスク、担当、ロールバック方法を記載する。

### Phase 3: 改善の実装（項目ごとに0.5〜2日）

以下は先行して実装するリストではなく、Phase 2 の結果に対応して選ぶ施策カタログである。

| 領域 | このプロジェクトでの重点確認箇所 | 適用候補 | 注意点 |
| --- | --- | --- | --- |
| 敵・ボス・エフェクト | `EnemyShooting`、`EnemyRangedAttack`、`LastBossController`、ドロップ・破壊エフェクト | 頻繁な生成・破棄が根拠ならオブジェクトプール化、初期化・後始末の統一 | ライフサイクル、当たり判定、演出終了、参照解除の回帰テストを必須にする。 |
| C# / GC | 高負荷フレームでのコレクション生成、文字列処理、ラムダ、LINQ、コルーチン | キャッシュ、バッファ再利用、非割当API、不要な更新処理の停止 | 可読性を落とす微小最適化は、計測効果が確認できる箇所に限定する。 |
| 2D物理 | `FixedUpdate`、Collider2D / Rigidbody2D、多数敵の接触・Raycast | レイヤー衝突表、形状、クエリ頻度、Fixed Timestep を見直す | 物理設定の全体変更は操作感・判定を変えるため、専用のプレイテストを行う。 |
| 2D描画 / URP | SpriteRenderer、Tilemap、半透明エフェクト、フォグ、背景、2Dライト | Sprite Atlas、共通マテリアル、オーバードロー削減、カリング、URP品質設定 | ドローコール数だけをKPIにせず、GPU時間と画質を同時に確認する。 |
| UI | Canvas、TextMeshPro、レイキャスト対象、レイアウト更新、SoftMask/UIEffect | Canvas分割、更新頻度低減、不要な Raycast Target / Mask の除去 | UIの見た目と入力範囲を自動・手動で確認する。 |
| アセット / メモリ | テクスチャ、AudioClip、Sprite Atlas、プリロード資産 | 端末別圧縮、不要な Read/Write・MipMap の解除、音声Load Type、サイズ削減 | 見た目・音質・ロード時間のトレードオフを比較画像・録音で承認する。 |
| ロード / 常駐 | シーン遷移、`Resources`、常駐マネージャー、アセット参照 | ロード単位と解放タイミングの明文化、非同期化・分割 | アセットを早く解放し過ぎて再ロードや参照切れを起こさない。 |
| Player / Build設定 | Developmentログ、IL2CPP、Stripping、シェーダーバリアント | Release設定を確認し、実測済みの不要データを削減 | ビルド設定の変更は各対象プラットフォームで起動・遷移・全演出を確認する。 |

各改善は小さな単位で実施し、次の順序を守る。

1. ベースラインのコミットと計測データを固定する。
2. 仮説、変更内容、期待する指標をチケットに書く。
3. 一つの仮説だけを変更する。
4. 同一条件でS1〜S5の該当シナリオを再計測し、Profile Analyzerの比較結果を残す。
5. 目標に寄与し、機能・見た目・メモリに退行がなければ採用する。寄与しなければロールバックする。

### Phase 4: 総合検証とリリース判定（1〜2日）

1. 改善後のビルドでS1〜S5を再計測し、ベースラインとの差分と成功条件を確認する。
2. 最低保証端末/PC、代表的な高性能端末/PC、可能なら長時間プレイで検証する。モバイルではウォームアップ後の熱による性能低下も記録する。
3. メモリスナップショットを再比較し、リーク修正が別の常駐増加を生んでいないか確認する。
4. 画質設定ごとに、UI、物理、演出、シーン遷移、ボス戦、セーブデータのスモークテストを行う。
5. 未達の指標は「追加調査」「仕様調整」「既知の制約」のいずれかに明確に分類し、未計測のまま完了にしない。

**成果物:** Before/After レポート、達成判定、既知の制約、リリース設定チェックリスト。

### Phase 5: 再発防止（継続）

1. 性能予算を `md` に残し、機能追加時の完了条件にフレーム時間・GC・メモリを加える。
2. 高負荷シナリオを手順化し、機能追加・大型アセット追加・URP設定変更時に再計測する。
3. コードレビューで、毎フレームのアロケーション、無制限な `Instantiate` / `Destroy`、探索APIの繰り返し呼び出し、不要な `Update`、無計画な品質設定変更を確認する。
4. 計測キャプチャと結果を変更単位に紐付け、性能の退行を追跡可能にする。

## 実施しないこと

- 計測前に、プロジェクト全体を一括でプール化・非同期化・品質低下させない。
- Editor計測だけで実機・Release相当ビルドの結果を代替しない。
- 平均FPSだけを改善指標にしない。フレームスパイク、P95/P99、メモリ、ロード、画質・操作感を併せて評価する。
- PDFのUnity 2020向け設定値を、Unity 6 / URPへ検証なしでそのまま適用しない。

## 最初の着手順

1. 性能保証対象と成功条件の未確定値を決める。
2. S1〜S5を実行できる計測用の操作手順を確定する。
3. Release相当ビルドでベースラインを採取し、最悪フレームとメモリ差分を共有する。
4. その結果から、最初の改善チケットを1件だけ選ぶ。
